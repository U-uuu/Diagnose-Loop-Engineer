# 智能诊断工作流

应用服务复用第二阶段的 Incident 和 Occurrence。上下文含故障摘要、发生记录和关联证据，项目摘要为可选字段。读取候选记录时独立获取时间最早的一条和最多 60 条近期记录，优先保留首末两条，再按来源和不同堆栈选择代表项。相同堆栈最多携带一次，默认最多 6 条发生记录、8 条证据，单条堆栈最多 1400 字符，序列化上下文最多 12000 字节。超出预算时先移除中间候选，再缩短保留记录。常见凭证模式与当前模型密钥在截断前脱敏。

节点按以下顺序运行。

```text
load_incident → build_context → diagnose → validate_diagnosis
→ plan_repair → validate_plan → save_result
```

Diagnosis Agent 生成带置信度的根因假设、真实证据引用和替代解释。校验节点检查证据编号，不确定时根因为 null，并保留待确认信息。Planning Agent 独立给出调查与验证步骤、建议修改、预期行为和风险。根因不明确时仅允许调查；当前阶段没有已核实的源码清单，因此目标文件列表必须为空，并记为需要人工审查。

日志和模型输出以不可信数据传递，提示词要求模型区分证据和推测。代码可校验证据编号和结构约束，无法自动验证模型自由文本中的每一项事实判断。脱敏覆盖常见凭证格式，需要人工审查特殊或业务敏感的数据。模型调用不带工具权限，诊断运行关闭外部工作流追踪。

SQLite 首次使用时通过可重复执行的新增 DDL 初始化 `diagnosis_runs`、`diagnosis_results` 和 `repair_plans`。运行记录先写入，成功时在一个事务中写入报告、引用证据快照、修复计划和已完成状态。普通节点失败会记录阶段、原因和可重试性；保存失败时回滚报告和计划，再单独保存失败状态。任务表保留用户输入的故障编号，以便记录编号不存在的失败。数据库整体不可写时 CLI 返回错误；进程被强制中断可能留下 RUNNING 状态。历史任务各自拥有独立编号。

诊断和规划分别允许一次结构格式修正，HTTP 临时错误按配置有限重试。流程使用同步 LangGraph，不使用 Checkpoint。报告记录成功模型调用的耗时、尝试次数，以及供应商返回的 Token 计数。扫描、历史、详情和计划查询均无需模型配置。
