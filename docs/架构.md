# 项目开发任务：AutoLoop Engineer（CLI 第一阶段）

你现在是一名资深 Python 架构师和 AI Agent 工程师。请负责开发一个名为 **AutoLoop Engineer** 的项目。

本项目的目标不是开发普通聊天机器人，而是构建一个基于 Multi-Agent 的自主软件诊断与修复系统。

当前只开发第一阶段：**Python CLI 命令行版本**。

请严格遵循工程化开发规范，优先保证架构清晰、模块职责单一、代码可维护、可测试，禁止把大量业务逻辑堆积在一个 Python 文件中。

# 一、项目目标

实现一个能够针对已有软件项目进行故障诊断和自动修复的命令行工具。

核心业务流程：

1. Discovery：发现项目中的故障。
2. Incident：将故障归纳为事件。
3. Diagnosis：分析故障原因。
4. Planning：生成修复计划。
5. Coding：修改项目代码。
6. Review：独立审查代码修改。
7. Testing：执行测试并验证修复结果。
8. Human Gate：等待人工确认。
9. Report：生成修复报告。

最终形成完整闭环：

发现问题 → 根因诊断 → 修复规划 → 代码修改 → 独立审查 → 自动测试 → 人工审批 → 输出报告。

第一阶段以本地项目和本地日志为主要数据来源。

# 二、技术选型

统一使用以下技术：

- Python 3.12
- uv：Python 项目与依赖管理
- LangGraph：Agent 工作流编排
- LangChain：模型与工具集成
- Pydantic：数据模型与数据校验
- Typer：CLI 命令行框架
- Rich：终端交互和执行进度展示
- python-dotenv：环境变量管理
- pytest：自动化测试
- GitPython 或 Git CLI：Git 操作

模型配置必须通过环境变量读取，不能将 API Key 硬编码在代码中。

模型调用应采用统一的客户端封装，避免各个 Agent 分别创建模型客户端。

# 三、系统架构

采用分层、模块化架构。

整体分为：

1. CLI 层：负责接收用户命令和展示结果。
2. Application 层：负责业务用例和流程入口。
3. Agent 层：负责不同角色的推理任务。
4. Workflow 层：负责 LangGraph 工作流编排。
5. Runtime 层：负责模型调用、上下文和执行管理。
6. Tools 层：提供文件、Git、Shell、测试等工具。
7. Discovery 层：负责日志扫描和故障发现。
8. Infrastructure 层：负责配置、持久化和外部依赖适配。
9. Schemas 层：定义模块之间的数据结构。

依赖规则：

- CLI 不直接实现业务逻辑。
- Agent 不直接控制整个业务流程。
- Workflow 负责组织 Agent 和确定性执行节点。
- Runtime 负责统一模型调用和运行上下文。
- Tools 负责提供具体执行能力。
- Application 负责协调业务用例。
- Schemas 负责跨模块的数据契约。
- Infrastructure 实现外部资源适配。

高层模块不能反向依赖底层具体实现，尽量遵循依赖倒置原则。

# 五、CLI 命令设计

最终希望支持以下命令：

```
# 查看帮助
autoloop --help

# 扫描指定项目
autoloop scan ./demo-project

# 查看发现的故障
autoloop incidents

# 分析指定故障
autoloop diagnose <incident-id>

# 自动修复指定故障
autoloop repair <incident-id>

# 查看修复报告
autoloop report <task-id>
```

这些命令是目标接口，不要求第一轮全部实现。

命令行层只负责参数解析、调用 Application 层和展示结果，不允许直接编写 Agent 推理逻辑。

# 六、Agent 与 Workflow 设计

采用 LangGraph 作为工作流引擎。

第一阶段设计以下角色：

### Diagnosis Agent

负责：

- 阅读故障日志。
- 分析异常堆栈。
- 定位可能存在问题的文件和代码。
- 给出根因分析。
- 输出诊断证据。

### Planning Agent

负责：

- 根据诊断结果制定修复计划。
- 确定需要修改的文件。
- 描述修改方案。
- 给出预期验证方式。

### Coding Agent

负责：

- 根据修复计划读取代码。
- 修改指定文件。
- 输出修改摘要。
- 记录 Git Diff。

### Review Agent

负责：

- 独立检查代码修改。
- 检查修改是否符合修复目标。
- 检查是否引入明显的新问题。
- 输出审查结论。

### Testing

测试执行必须优先使用确定性脚本或命令，而不是让 LLM 假装执行测试。

负责：

- 执行项目测试。
- 执行构建命令。
- 收集退出码和测试输出。
- 判断是否通过。

LLM 可以负责解释测试结果，但不能伪造测试执行结果。

### Human Gate

在关键操作前暂停工作流，等待用户确认。

尤其是：

- 执行有风险的 Shell 命令。
- 接受代码修改。
- 确认最终修复结果。

后续可以使用 LangGraph Checkpoint 和 Interrupt 实现暂停与恢复。

注意：第一阶段不需要一次性实现所有 Agent。先实现最小可运行 Workflow，再逐步扩展。

# 七、工程安全要求

这是一个能够修改用户代码和执行命令的工具，必须设计安全边界。

1. 只能操作用户明确指定的项目目录。
2. 文件读写必须进行路径校验，防止路径穿越。
3. 默认不能直接修改用户主分支。
4. 修改代码前检查 Git 状态。
5. 优先在独立 Git 分支或 Git Worktree 中执行修复。
6. 危险 Shell 命令必须要求人工确认。
7. 禁止自动执行删除磁盘、修改系统配置等高风险命令。
8. API Key 和敏感配置不得写入日志。
9. 记录 Agent 的执行步骤、工具调用、异常和测试结果。
10. 测试失败时不能宣称修复成功。

第一阶段可以先采用本地受限执行模式，Docker 沙箱后续再实现。

# 九、代码质量规范

必须遵循以下要求：

1. 单一职责原则：一个模块只承担明确职责。
2. 高内聚、低耦合。
3. 业务逻辑与基础设施分离。
4. 模型调用与业务逻辑分离。
5. Agent Prompt 与 Python 业务代码分离，优先采用独立 Prompt 文件或清晰的模板模块。
6. 输入输出使用 Pydantic Schema 或明确的类型定义。
7. 合理使用类型注解。
8. 统一异常处理。
9. 统一日志格式。
10. 关键业务逻辑必须有测试。
11. 避免不必要的抽象和设计模式。
12. 禁止单个文件承载大量不相关功能。
13. 禁止重复实现已有工具能力。
14. 不要为了追求所谓的架构完整而过度设计。
15. 每个模块必须有明确的职责和依赖边界。

代码风格以专业、简洁、可维护为目标，不要生成大量没有实际意义的封装、注释和模板代码。
